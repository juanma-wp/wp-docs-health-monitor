Building an edit form

Positives

  • The doc correctly describes the distinction between getEntityRecord (returns the server-persisted record with title as an object containing rendered/raw) and getEditedEntityRecord (returns the merged record with title as a plain string after edits). This matches the selector implementations in packages/core-data/src/selectors.ts where getEditedEntityRecord spreads raw and edited state together.
  • The doc accurately states that saveEditedEntityRecord returns a promise that resolves with the updated record on success and an empty/falsy value on failure. The source in packages/core-data/src/actions.js confirms: return await dispatch.saveEntityRecord(...) which returns updatedRecord (the API response) on success and undefined implicitly when hasEditsForEntityRecord is false or config is missing.
  • GAP: The editEntityRecord action accepts an options object with an undoIgnore boolean (visible in packages/core-data/src/actions.js as options.undoIgnore). The doc never mentions this option, which lets callers make edits that are excluded from undo history — useful for programmatic/transient changes that should not pollute the undo stack.
