💡

Update the BlockDeprecation.isEligible type signature in types.ts to include the third data parameter, and ensure the documentation matches the runtime behaviour.

  • The runtime call in apply-block-deprecated-versions.ts (line ~58) passes a third argument { blockNode: rawBlock, block } to isEligible, so the third parameter IS available to developers who declare it.
  • The public type in types.ts declares isEligible as ( attributes: OldAttributes, innerBlocks: Block[] ) => boolean — only two parameters — which means TypeScript will reject any user-written isEligible that declares a third data parameter.
  • Either update the type to ( attributes: OldAttributes, innerBlocks: Block[], data: { blockNode: RawBlock; block: Block } ) => boolean, or remove the data parameter documentation from the deprecation page to match the declared public contract.

Positives

  • The doc accurately describes the migrate return type as Object | Array (either new attributes or a tuple [attributes, innerBlocks]), which matches the code's NewAttributes | [ NewAttributes, Block[] ] return type in types.ts.
  • The doc correctly states that a deprecation's migrate will not be run if its save function does not return a valid block — confirmed by the runtime code in apply-block-deprecated-versions.ts which only calls migrate after isValid is confirmed true.
  • GAP: The BlockDeprecation interface in types.ts includes an apiVersion?: number property that is not documented on the deprecation page. Block authors who need to specify the API version for a deprecated block form have no documentation to guide them.
