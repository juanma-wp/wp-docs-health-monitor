const isLockValid =
				lock === universalUnlock ||

💡

Update the private stores example to clarify the exact conditions under which the second store() call throws.

  • The second call store('myPlugin/private', { /* store part */ }) passes lock = false (the default). The isLockValid check evaluates to false because false !== universalUnlock AND (false !== true && false === true) is also false. So the example comment "The following call throws an Error!" is correct for a call with no lock.
  • However, the example is misleading because a second call with lock: true would ALSO throw (since lock !== true is false in the isLockValid expression, making the whole expression false). Only a second call passing the exact same string lock value (or universalUnlock) would succeed.
  • Add a clarifying note: "Any subsequent store() call for this namespace must pass the same lock string (not true) or the universalUnlock string to access the private store. Passing lock: true again on a second call will also throw, because true is only valid on the *first* call to set the lock."

Positives

  • The withSyncEvent() documentation accurately describes the function's purpose and the specific event properties/methods that require synchronous access (event.preventDefault(), event.stopPropagation(), event.stopImmediatePropagation(), event.currentTarget), matching the implementation in utils.ts where withSyncEvent sets callback.sync = true.
  • The watch() function documentation correctly describes it as equivalent to effect from @preact/signals (the source exports export const watch = effect) and accurately documents the cleanup function pattern and the unwatch() return value.
  • GAP: The getElement() function returns an object with ref and attributes only, but the doc implies a local reactive state is also present ("contains a reference to the DOM element, its props and a local reactive state"). The actual implementation in scopes.ts returns only { ref: ref.current, attributes: deepReadOnly(attributes) } — there is no local reactive state key in the returned object. Developers looking for a reactive state property on the getElement() result will not find one.
