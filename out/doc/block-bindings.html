💡

Update the add_filter example for block_bindings_source_value to declare 5 accepted arguments instead of 2.

  • Change add_filter( 'block_bindings_source_value', 'wpmovies_format_visualization_date', 10, 2 ) to add_filter( 'block_bindings_source_value', 'wpmovies_format_visualization_date', 10, 5 )
  • Update the callback signature to reflect all 5 parameters: function wpmovies_format_visualization_date( $value, $name, $source_args, $block_instance, $attribute_name )
  • Note that registering with accepted_args = 2 means the callback only receives $value and $name, silently losing access to $source_args, $block_instance, and $attribute_name

Positives

  • The block_bindings_source_value filter parameters (value, name, source_args, block_instance, attribute_name) are accurately documented and match the apply_filters call in class-wp-block-bindings-source.php exactly.
  • The registerBlockBindingsSource JS API documentation accurately reflects the TypeScript source in packages/blocks/src/api/registration.ts, including all optional properties (label, usesContext, getValues, setValues, canUserEditValue, getFieldsList) and the validation logic that requires name and either label or a pre-registered server label.
  • GAP: The getFieldsList function receives { select, context } as its argument (visible in packages/blocks/src/store/private-selectors.ts via getBlockBindingsSourceFieldsList), but the doc's getFieldsList example shows it called with no arguments (getFieldsList()). Developers implementing getFieldsList to use store selectors or block context would not know these are available.
