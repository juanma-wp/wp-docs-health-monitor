major type-signature confidence: 90%
It receives the block settings, the name of the registered block, and either null or the deprecated block settings (when applied to a registered deprecation) as arguments.

gutenberg:packages/blocks/src/store/process-block-type.ts

applyFilters(
						'blocks.registerBlockType',
						// Merge deprecation keys with pre-filter settings
						// so that filters that depend on specific keys being
						// present don't fail.
						{
							// Omit deprecation keys here so that deprecations
							// can opt out of specific keys like "supports".
							...omit( blockType, DEPRECATED_ENTRY_KEYS ),
							...deprecation,
						},
						blockType.name,
						deprecation
					)
💡

Update the blocks.registerBlockType filter signature description to accurately describe the third argument when applied to a deprecation entry.

  • Change 'the deprecated block settings' to 'the original deprecation entry object' (i.e., the raw deprecation object before merging with the block type settings).
  • Clarify that the first argument (block settings) passed to the filter for deprecations is a *merged* object — the block type settings with deprecation keys spread on top — not the raw deprecated block settings alone.
  • Suggested revised sentence: 'It receives the block settings, the name of the registered block, and either null (for the initial registration call) or the original deprecation entry object (when applied to a registered deprecation) as arguments.'

Positives

  • The render_block and render_block_{block_name} filter callback parameter lists (3 params: $block_content, $block, $instance) are correctly documented and match the apply_filters calls in class-wp-block.php.
  • The blocks.getBlockAttributes filter callback signature (4 parameters: blockAttributes, blockType, innerHTML, attributes) is correctly documented and matches the applyFilters call in packages/blocks/src/api/parser/get-block-attributes.ts.
  • GAP: The blocks.registerBlockType filter is also applied to each deprecation entry with the deprecation object as the third argument (not just null), and the code in process-block-type.ts shows the merged object passed — developers writing filters that need to distinguish initial registration from deprecation processing would benefit from a more precise description of what the third argument contains in each case.
