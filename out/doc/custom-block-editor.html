💡

Update the framing sentence to name <BlockCanvas> as the key rendering component, not <BlockList>.

  • Change "The key components are <BlockEditorProvider> and <BlockList>." to "The key components are <BlockEditorProvider> and <BlockCanvas>."
  • Update the subsequent explanation to describe <BlockCanvas> as the component that renders the editable block area inside an iframe, noting that it internally defaults to rendering <BlockList> as its children (see children = <BlockList /> in ExperimentalBlockCanvas).
  • <BlockList> is still a valid architectural detail but should be described as an internal implementation of <BlockCanvas>, not as the component a developer directly uses in the custom editor example.

Positives

  • The doc correctly describes <BlockEditorProvider> props: value (array of block objects), onInput (for in-memory updates), onChange (for persistence), and settings — all of which match the JSX snippet shown and the component's documented contract.
  • The use of createRoot from react-dom and domReady from @wordpress/dom-ready in the src/index.js bootstrap snippet is accurate and reflects the modern React 18 rendering API.
  • GAP: registerCoreBlocks in packages/block-library/src/index.js accepts an optional blocks array parameter (defaulting to __experimentalGetCoreBlocks()), allowing callers to register only a subset of core blocks. The doc calls registerCoreBlocks() with no arguments but never mentions this customisation capability, which would be useful for custom editors that want to restrict available blocks.
