Positives

  • The doc correctly identifies both parameters passed to block_editor_settings_all callbacks — $settings (array) and $context (WP_Block_Editor_Context instance) — which matches the filter call at L671 of src/wp-includes/block-editor.php: apply_filters( 'block_editor_settings_all', $editor_settings, $block_editor_context ).
  • The four wp_theme_json_data_* filter hook names (wp_theme_json_data_default, wp_theme_json_data_blocks, wp_theme_json_data_theme, wp_theme_json_data_user) are all confirmed present and firing in src/wp-includes/class-wp-theme-json-resolver.php at lines 175, 425, 292, and 572/601 respectively.
  • GAP: The blockEditor.useSetting.before filter (documented in the JS section) passes undefined as the initial settingValue to the filter — not the resolved setting value — and only uses the filter's return value if it is not undefined. This means a callback that returns undefined is a no-op and the setting falls through to the normal resolution chain. The doc does not mention this behaviour, which could surprise developers who expect to be able to suppress a setting by returning undefined.
