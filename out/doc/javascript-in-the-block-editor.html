Positives

  • The doc correctly identifies registerBlockVariation as the function to use from the blocks package, and the exported API symbols confirm it exists as registerBlockVariation: (blockName: string, variation: BlockVariation | BlockVariation[]) => void in packages/blocks/src/api/registration.ts.
  • The doc correctly states that enqueue_block_editor_assets is the right hook for scripts that need to run in the Block Editor — the hook fires in edit-form-blocks.php (L339), site-editor.php (L308), and widgets-form-blocks.php (L83), confirming it is the canonical hook for this purpose.
  • GAP: The doc's wp_enqueue_script example passes a plain boolean false as the last argument (the $args / $in_footer parameter). Since WordPress 6.3, this parameter was overloaded to accept an array with strategy, in_footer, and (since 6.9) fetchpriority keys. The doc never mentions this extended form, which developers would benefit from knowing when they need deferred or async loading of their variation scripts.
