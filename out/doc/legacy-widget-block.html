💡

Fix the widget() method signature in the documentation example.

  • Change public function widget( $instance ) to public function widget( $args, $instance ) to match the actual WP_Widget::widget( $args, $instance ) signature defined in src/wp-includes/class-wp-widget.php (line 114).
  • WordPress calls $this->widget( $args, $instance ) (line 394 of the same file), so a subclass with only one parameter will receive $args (the display arguments array containing before_widget, after_widget, before_title, after_title) silently bound to $instance, and the real $instance settings array will be missing entirely — causing incorrect rendering or PHP warnings.
  • All references to $instance['name'] and other instance keys in the example body will be reading from the wrong variable.

Positives

  • The registerLegacyWidgetBlock function name and its location in @wordpress/widgets are correctly documented — the exported symbol exists in packages/widgets/src/index.js exactly as described.
  • The widget_types_to_hide_from_legacy_widget_block filter name is accurate — it fires at src/wp-includes/block-editor.php L260 as apply_filters('widget_types_to_hide_from_legacy_widget_block', ...), matching the doc's PHP example exactly.
  • GAP: registerLegacyWidgetBlock accepts a supports parameter (defaulting to {}) that lets callers override block support settings. The doc's PHP enqueue example calls wp.widgets.registerLegacyWidgetBlock() with no arguments, but never mentions that a supports object can be passed to customise block supports for the Legacy Widget block in the given editor context.
